# Telegram-агент БАРС

Flue принимает Telegram webhook, вызывает OpenAI-совместимую модель и хранит диалоги в PostgreSQL. FastAPI обслуживает авторизацию и управление сотрудниками. Простой текст в личном чате идёт агенту. Команды `/start` и `/reset` работают без модели. `/reset` открывает новый диалог, предыдущий сохраняется в PostgreSQL.

## Запуск

### Локальная разработка

`docker-compose-dev.yml` поднимает PostgreSQL 17 с базой `hackathon`, Redis, Flue, файловый сервис, отдельную БД файлового сервиса и MinIO. API запускается локально. Flue обращается к нему через `host.docker.internal:8000` (порт задаётся через `API_PORT`).

В корневом `.env` задайте `FILE_DB_PASSWORD` и `MINIO_ROOT_PASSWORD` разными случайными значениями от 32 символов. Остальные настройки файлового сервиса доступны в `.env.example`.

Для Flue в корневом `.env` также заполните `BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET_TOKEN`, `BOT_API_TOKEN`, `CHAT_BASE_URL`, `CHAT_MODEL` и при необходимости `CHAT_API_KEY`. Значение `BOT_API_TOKEN` должно совпадать с настройкой локального API. Если модель работает на этом же компьютере, используйте в `CHAT_BASE_URL` адрес `host.docker.internal`, не `localhost` и не адрес FastAPI.

Из корня проекта:

```powershell
docker compose -f docker-compose-dev.yml up -d --build --wait
```

Для локального API в `api/.env` задайте `DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/hackathon` и `REDIS_URL=redis://127.0.0.1:6379/0`, а также секреты приложения. Если меняли `POSTGRES_PORT` или `REDIS_PORT`, укажите те же порты в URL. Переменные текущего терминала имеют приоритет над `.env`.

```powershell
cd api
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn main:app --host 0.0.0.0 --reload
```

Адреса по умолчанию: API — `http://127.0.0.1:8000/docs`, Flue — `http://127.0.0.1:3000/health`, файловый сервис — `http://127.0.0.1:8080/file-service/docs`, MinIO Console — `http://127.0.0.1:9001`. Миграции файлового сервиса и создание bucket выполняются при старте его контейнера; миграции API применяются командой выше. API слушает `0.0.0.0` для доступа из контейнера Flue; ограничьте входящий доступ средствами брандмауэра.

Не запускайте dev-compose и полный Compose одновременно на одинаковых портах. Их основные PostgreSQL используют разные версии, базы и volumes; данные автоматически не переносятся. Не меняйте версию PostgreSQL для существующего volume и не удаляйте volumes для перезапуска.

### Полный запуск в Docker

1. Скопируйте `.env.example` в `.env`. Укажите токен бота в `BOT_TOKEN`, произвольный независимый `TELEGRAM_WEBHOOK_SECRET_TOKEN` и настройки модели. `CHAT_BASE_URL` — базовый URL совместимого API, например `https://provider.example/v1`. При работе без авторизации оставьте `CHAT_API_KEY` пустым.
2. Выполните `docker compose up -d --build --wait`. FastAPI применит миграции, Flue создаст таблицы агента и обработки Telegram. Новый volume называется `bars-hackathon_postgres_flue_data`. Volume прежнего Python-бота можно сохранить для отката.
3. Проверьте `http://127.0.0.1:3000/health` с хоста. FastAPI доступен внутри Compose по адресу `http://api:8000`. Для второго экземпляра используйте другое имя проекта Compose, другие хостовые порты и отдельный тестовый токен.

## Файловый сервис и MinIO

Добавьте в корневой `.env`:

```dotenv
FILE_SERVICE_PORT=8080
FILE_DB_USER=file_service
FILE_DB_PASSWORD=replace-with-a-long-random-database-password
MINIO_ROOT_USER=file_storage_admin
MINIO_ROOT_PASSWORD=replace-with-another-long-random-storage-password
MINIO_API_PORT=9000
MINIO_CONSOLE_PORT=9001
S3_BUCKET_NAME=files
```

Замените оба пароля разными случайными значениями, желательно от 32 символов; MinIO требует минимум 8 символов. Остальные значения можно оставить как в примере. Для генерации пароля можно выполнить `python -c "import secrets; print(secrets.token_urlsafe(32))"`. В Docker Compose отдельный `file-service/.env` не нужен: `DB_*` и `S3_*` передаются сервису из корневых настроек автоматически.

Запуск файлового сервиса: `docker compose up -d --build --wait file-service`. Используется уже существующий сервис `postgres` и отдельная база с именем `file-service`. Одноразовый контейнер `file-db-init` создаёт отсутствующего пользователя и БД; это клиент `psql`, а не второй сервер PostgreSQL. Подготовка работает и с уже инициализированным PostgreSQL. File-service сначала применяет свои миграции через asyncpg, затем создаёт отсутствующий bucket в MinIO и запускает HTTP-сервер.

- File-service: `http://127.0.0.1:8080/file-service/docs`.
- S3 API MinIO: `http://127.0.0.1:9000`.
- Консоль MinIO: `http://127.0.0.1:9001`, вход по `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`.
- Внутри Compose file-service доступен по `http://file-service:3000`, а MinIO — по `http://minio:9000`.

Метаданные файлов хранятся в базе `file-service` общего PostgreSQL, в существующем volume `postgres_flue_data`; объекты — в `minio_data`. Пользователь БД задаётся через `FILE_DB_USER`, пароль — через `FILE_DB_PASSWORD`. Имя базы фиксировано, переменная `FILE_DB_NAME` больше не используется. Миграции файлового сервиса выполняются только в его базе и не затрагивают БД основного API. Порты проброшены только на `127.0.0.1` и могут быть изменены переменными из примера.

Если раньше запускался отдельный `file-postgres`, его старый volume не удаляется автоматически. Данные из него нужно отдельно перенести через `pg_dump` / `pg_restore` до переключения сервиса; пустая новая база не заменяет такой перенос. Изменение `FILE_DB_PASSWORD` в `.env` не меняет пароль уже существующего пользователя PostgreSQL.

Bucket по умолчанию приватный. Текущий file-service возвращает в поле `url` внутренний S3-адрес, а не публичную или подписанную ссылку; для доступа к объектам нужны S3-учётные данные либо вход в консоль MinIO.

Готовые официальные образы MinIO недоступны в проверенных реестрах. Используется community-сборка `netvark/minio` с открытым процессом сборки, закреплённая по digest `sha256:77281ea99af0d02e2880e91d345bf81cae584454aedffbb7912331774f42d4bf`. Community-версия MinIO больше не поддерживается: этот контур предназначен для локальной разработки, а для публичного production-хранилища нужен поддерживаемый S3-сервис.

## Документация API

Swagger UI доступен на `http://127.0.0.1:8000/docs`, схема OpenAPI — на `http://127.0.0.1:8000/openapi.json`. В Swagger можно посмотреть и вызвать ручки входа, сотрудников, приглашений и проверки состояния API. Порт API в Docker Compose можно изменить через `API_PORT` в `.env`; доступ с хоста открыт только на `127.0.0.1`.

## Техническая аналитика

Обычный `docker compose up -d --build` запускает OpenTelemetry Collector, Prometheus и Tempo. Flue отправляет трассы и метрики в Collector, FastAPI читает агрегаты из Prometheus. Сервисы телеметрии доступны внутри сети Compose. Метрики хранятся 14 дней, трассы — 7 дней. Трассировка Flue использует `content: false`.

Фронт читает `GET /analytics/technical?range=24h` с `Authorization: Bearer <access_token>`. Доступные периоды — `1h`, `24h` (по умолчанию) и `7d`. Границы периода в UTC, все длительности в миллисекундах. Ручка обновляется по мере выгрузки метрик, каждые 15 секунд.

```json
{
  "range": "24h",
  "from_at": "2026-11-14T10:00:00Z",
  "to_at": "2026-11-15T10:00:00Z",
  "tokens": {
    "chat": {"input": 1200, "output": 90, "by_model": [{"model": "example", "input": 1200, "output": 90}]},
    "document_import": {"input": 0, "output": 0, "by_model": []}
  },
  "response_time": {"sample_count": 10, "mean_ms": 1200, "p95_ms": 2100},
  "stages": [
    {"stage": "queue", "mean_ms": 20},
    {"stage": "preparation", "mean_ms": 1100},
    {"stage": "delivery", "mean_ms": 80}
  ],
  "agent_breakdown": [
    {"kind": "model", "name": "example", "mean_ms": 490},
    {"kind": "tool", "name": "answer_from_docs", "mean_ms": 610},
    {"kind": "rag", "name": "search", "mean_ms": 120},
    {"kind": "rag", "name": "compose", "mean_ms": 470}
  ],
  "delivery": {
    "answer": {"sent": 10, "failed": 1, "unknown": 0},
    "fallback": {"sent": 1, "failed": 0, "unknown": 0},
    "service": {"sent": 1, "failed": 0, "unknown": 0}
  }
}
```

Три `stages` складываются в длительность ответа. `agent_breakdown` показывает среднее на один вызов модели, инструмента или шага RAG. Эти замеры могут перекрываться. Расход берётся из модельных вызовов Flue, входные токены включают токены кэша. p95 оценивается по гистограмме Prometheus. При пустой выборке длительности равны `null`, а счётчики — `0`. При недоступности Prometheus API возвращает `503`.

## Вложения к заявкам Jira

Настройки Jira задаются в `api/.env` для локального API и в корневом `.env` для полного Compose.

```dotenv
JIRA_BASE_URL=https://your-company.atlassian.net
JIRA_EMAIL=integration@example.com
JIRA_API_TOKEN=
JSM_SERVICE_DESK_ID=1
JSM_REQUEST_TYPE_ID=1
```

Замените адрес, email и ID на свои значения. Корневой `.env` имеет приоритет над `api/.env`, переменные окружения имеют приоритет над файлами. После изменения настроек перезапустите локальный API или выполните `docker compose up -d --wait api` для полного Compose.

Для Jira Cloud API-токен создаётся в аккаунте Atlassian: https://id.atlassian.com/manage-profile/security/api-tokens → Create API token → имя и срок действия → Create → Copy. `JIRA_EMAIL` должен принадлежать владельцу токена. Для адреса `https://your-company.atlassian.net` используется токен без scopes. Для токена со scopes нужен `JIRA_BASE_URL=https://api.atlassian.com/ex/jira/<cloudId>` и права на чтение заявок, создание заявок и прикрепление файлов. Права учётной записи на проект JSM также обязательны. Это настройка Jira Cloud; Jira Data Center использует другой способ выдачи и применения токенов.

Для доступа к ручке вложений отправляйте `X-Bot-Token` со значением `BOT_API_TOKEN`. При обращении к Jira сервер использует `JIRA_EMAIL` и `JIRA_API_TOKEN` для Basic Auth.

`POST /private/tickets/{ticket_id}/attachments` прикрепляет один файл к заявке, созданной через `POST /tickets`. В адресе передаётся локальный `tickets.id`, API сам находит заявку Jira по сохранённым `external_id`/`external_key`.

`POST /tickets` при создании заявки сохраняет из ответа Jira внешний ID (`issueId`) и ключ (`issueKey`), возвращает их в полях `external_id` и `external_key`. Заявки, созданные до этой правки, полей не имеют: для них вложения вернут `400`, нужна новая заявка.

В полном Compose Flue обращается к ручке по адресу `http://api:8000/private/tickets/{ticket_id}/attachments`. На сервере Nginx блокирует внешние запросы к `/private/`.

Тело запроса — `multipart/form-data`: обязательное поле `file` и необязательное `public` (по умолчанию `false`, вложение доступно только сотрудникам поддержки). Для внутреннего вложения учётной записи интеграции нужны права агента JSM. `public=true` делает вложение доступным клиенту. Размер файла — от 1 байта до 10 МиБ; ограничения самой Jira также применяются.

```powershell
curl.exe -X POST "http://127.0.0.1:8000/private/tickets/2/attachments" -H "X-Bot-Token: $env:BOT_API_TOKEN" -F "file=@conversation.txt" -F "public=false"
```

При успехе API возвращает `201` с полями `issue_id_or_key` (ключ заявки Jira), `comment_id`, `filename`, `public`. Ошибки: `400` — некорректный или пустой файл, отказ Jira по входным данным или у заявки нет привязки к Jira; `401` — отсутствует или неверен `X-Bot-Token`; `404` — заявки нет в нашей БД либо заявка/сервис-деск не найдены в Jira; `413` — превышение размера; `422` — неверный ID либо формат формы; `502` — транспортная ошибка, некорректный ответ или другая ошибка Jira.

Эндпоинт не создаёт тикет и не меняет локальную БД. Повторная успешная отправка добавляет новое вложение. При тайм-ауте результат может быть неизвестен: перед повтором проверьте вложения в Jira.

## Confluence

`GET /confluence/pages?space_id=D1uivli2U08p&page_id=491522` получает страницу через Confluence Cloud REST API v2. Передавайте заголовок `X-Bot-Token` со значением `BOT_API_TOKEN`. В `space_id` можно передать числовой ID пространства или его ключ из URL. При несовпадении пространства и страницы API возвращает `404`.

В корневом `.env` задайте `CONFLUENCE_BASE_URL` (например, `https://barsdocs.atlassian.net/wiki`), `CONFLUENCE_EMAIL` владельца токена и `CONFLUENCE_API_TOKEN`. Docker Compose передаёт эти настройки в API. Токен хранится только в локальном `.env`, который исключён из Git.

Ответ содержит `page_id`, `space_id`, `space_key`, `title`, `status`, `content_html`, `version`, `updated_at` и `url`. `content_html` — HTML-представление страницы, не список дочерних новостей; его нельзя вставлять в интерфейс без санитизации. `updated_at` — время создания последней версии страницы. Данные не сохраняются в БД.

Без `X-Bot-Token` или с неверным значением возвращается `401`, при отсутствии страницы или пространства — `404`, при ошибках Confluence — `502`, при отсутствии настроек — `503`, при таймауте — `504`.

### Переиндексация по вебхуку

Задайте отдельный случайный `CONFLUENCE_WEBHOOK_SECRET` в корневом `.env`.
Для одного пространства задайте его числовой ID в `CONFLUENCE_SPACE_ID`.
Тогда Flue берёт пространство из настроек и читает ID страницы из `page_id` или `id`.
Добавьте точный маршрут в HTTPS-блок Nginx для `api.cheremha.ru`. Используйте
хостовый порт Flue из `FLUE_PORT`, по умолчанию `3000`.

```nginx
location = /flue/channels/confluence/webhook {
    proxy_pass http://127.0.0.1:3000/channels/confluence/webhook;
}
```

В Automation нужного пространства выберите [Page edited](https://support.atlassian.com/cloud-automation/docs/triggers-in-confluence-automation/#Page-edited)
и [Send web request](https://support.atlassian.com/cloud-automation/docs/actions-in-confluence-automation/#Send-web-request).
Метод `POST`, адрес `https://api.cheremha.ru/flue/channels/confluence/webhook`,
заголовки `Content-Type: application/json` и скрытый `X-Webhook-Secret: <CONFLUENCE_WEBHOOK_SECRET>`.
В поле Custom data укажите JSON.

```json
{"space_id":"{{space.id}}","page_id":"{{page.id}}"}
```

Если пространство задано на сервере, действующие правила могут присылать
`{"id":"{{page.id}}","type":"updated"}` и `{"id":"{{page.id}}","type":"new"}`.
Оба события ставят страницу в очередь импорта.

Для уже настроенного события Page deleted передайте `{"id":"{{page.id}}","type":"deleted"}`.
Если пространство не задано на сервере, добавьте `"space_id":"{{space.id}}"`.
Ответ `204` подтверждает удаление источника из поиска. Воркер очищает фрагменты в Qdrant в фоне.

Сохраните правку тестовой страницы и проверьте `202` в журнале Automation.
Этот ответ подтверждает запись задания. Результат импорта виден в `GET /rag/jobs`.
Повтор той же опубликованной версии получает статус `skipped` в истории
(`include_history=true`). При ошибке импорта бот использует последнюю успешно
индексированную версию. Фрагменты импортированных страниц доступны пользователям
бота и содержат ссылку на страницу Confluence.

## Авторизация администратора

Задайте случайный `JWT_SECRET` длиной не менее 32 символов в `.env`. Секрет должен оставаться одинаковым между перезапусками и экземплярами API. Срок действия JWT задаётся через `JWT_ACCESS_TOKEN_EXPIRE_MINUTES` и по умолчанию составляет 60 минут.

Миграция `0004` создаёт администратора `admin@example.com` с временным паролем `admin`. Миграция `0005` удаляет старых Telegram-пользователей, тикеты и сообщения тикетов, а таблицу `admins` переименовывает в `users`, сохраняя аккаунты для входа. Удалённые данные при откате не восстанавливаются. В БД хранится только bcrypt-хеш пароля. Эти реквизиты предназначены только для разработки.

`POST /auth/login` принимает JSON с полями `email` и `password` и возвращает `access_token` и `token_type: "bearer"`. Регистрации и обновления токена нет. Для всех ручек `/employees` передавайте заголовок `Authorization: Bearer <access_token>`. Без действующего токена API возвращает `401`. В Swagger нажмите **Authorize** и вставьте полученный токен без префикса `Bearer`.

## Кэш сотрудников и отзыв доступа

Проверочные ручки сотрудников сохраняют прежние адреса и авторизацию. При поиске по `telegram_id` API сначала читает Redis. Если записи нет, API обращается в PostgreSQL и кэширует только найденного сотрудника на 180 секунд. Чтение не продлевает TTL. Отсутствующий сотрудник не кэшируется: API возвращает `404`, бот сообщает об отсутствии доступа.

`DELETE /employees/{employee_id}` требует JWT, очищает кэш и удаляет сотрудника из PostgreSQL; успех — `204`, неизвестный UUID — `404`. Заполнение кэша и удаление синхронизируются по `telegram_id`, чтобы параллельная проверка не восстановила запись после удаления. После успешного удаления следующая проверка бота отказывает в доступе. При недоступном Redis проверка и удаление возвращают `503`, а не предоставляют доступ по умолчанию.

Удалять сотрудника нужно через API. Прямое удаление SQL-запросом не очищает Redis: такая запись останется до истечения TTL.

В Docker Compose Redis запускается автоматически. Для локальной разработки выполните `docker compose -f docker-compose-dev.yml up -d redis`; API по умолчанию использует `redis://127.0.0.1:6379/0`. Другой адрес можно задать через `REDIS_URL`; порт Redis в dev-compose — через `REDIS_PORT`.

## Редактирование ФИ сотрудника

`PATCH /employees/{employee_id}` требует JWT администратора в заголовке `Authorization: Bearer <access_token>`. `employee_id` — UUID сотрудника из списка `/employees`.

```json
{
  "first_name": "Иван",
  "last_name": "Иванов"
}
```

Можно передать только одно поле: отсутствующее останется без изменений, а `null` очистит значение. Максимальная длина каждого поля — 255 символов. Пустое тело `{}`, посторонние поля и некорректный UUID возвращают `422`. `telegram_id`, `username`, `is_parsed` и дата создания не меняются.

Успех — `200` с обновлённым `EmployeeRead`; неизвестный сотрудник — `404`, недоступный Redis — `503`. Кэш обновляется сразу под той же блокировкой, что чтение, удаление и обновление данных из Telegram.

## Данные сотрудника из Telegram

Миграция `0008` добавляет `employees.is_parsed` со значением `false` по умолчанию, в том числе для существующих сотрудников. `POST /employees` создаёт сотрудника с `is_parsed: false`. При первом сообщении бот читает этот флаг и, если данные ещё не получены, вызывает `PATCH /private/employees/by-telegram-id/{telegram_id}` с `X-Bot-Token`.

PATCH принимает три обязательных nullable-поля: `username`, `first_name`, `last_name`. Он сохраняет полученные значения и устанавливает `is_parsed: true`, даже если все значения — `null`. В ответе — обновлённый `EmployeeRead`. Неизвестный сотрудник — `404`. Повторный PATCH уже обработанного сотрудника возвращает текущие данные без перезаписи. Кэш Redis обновляется сразу, без ожидания истечения TTL. Сведения не запрашиваются у пользователя вручную.

## Приглашения сотрудников

Укажите `TELEGRAM_BOT_USERNAME` без `@` и задайте независимый случайный `BOT_API_TOKEN` длиной не менее 32 символов в `.env`. API и Flue должны использовать одинаковый `BOT_API_TOKEN`. Для локального запуска Flue также задайте `API_URL`, например `http://127.0.0.1:8000`; в Docker Compose адрес уже настроен.

Все ручки `/invites` требуют JWT:

- `POST /invites` — создать приглашение и получить `link` вида `https://t.me/<bot_username>?start=invite_<id>`. Тело: `count_of_use` (по умолчанию 1), необязательные `first_name` и `last_name`. ФИ разрешено только для одноразового приглашения. Без `TELEGRAM_BOT_USERNAME` ручка возвращает `503` и не создаёт запись.
- `GET /invites?page=1&page_size=20` — список действующих приглашений, размер страницы до 100.
- `GET /invites/{id}` — получить приглашение и оставшееся число использований.
- `DELETE /invites/{id}` — отозвать приглашение, ответ `204`.

После `/start invite_<id>` или `/start <id>` бот сразу вызывает `POST /private/invites/{id}/accept`, передавая `telegram_id`, `username`, `first_name` и `last_name` из данных Telegram; отсутствующие значения передаются как `null`. Сотрудник создаётся сразу с `is_parsed: true`. Вводить имя и фамилию не нужно. При `201` бот подтверждает доступ. Уже добавленный сотрудник получает подтверждение без повторного использования инвайта. При ошибке активации бот сообщает об отказе.

На каждом сообщении бот обращается к `GET /private/employees/by-telegram-id/{telegram_id}`. Он передаёт `X-Bot-Token` в приватные ручки сотрудников и приглашений основного API. Отдельный внутренний API вложений не требует этого заголовка. Запросы к агенту доступны только действующим сотрудникам.

ФИ из персонального приглашения имеет приоритет над данными Telegram. После создания сотрудника число использований уменьшается; последнее использование удаляет приглашение. Создание сотрудника и списание выполняются отдельными сохранениями без общей транзакции и блокировок: при параллельных запросах или сбое между сохранениями возможна рассинхронизация.

## Публичный webhook

Добавьте маршрут webhook в HTTPS-блок `api.cheremha.ru` в Nginx.

```nginx
location = /channels/telegram/webhook {
    limit_except POST { deny all; }
    proxy_pass http://127.0.0.1:3000;
}
```

На тестовом токене проверьте доступность TLS и зарегистрируйте webhook. Следующий пример PowerShell предполагает, что `BOT_TOKEN` и `TELEGRAM_WEBHOOK_SECRET_TOKEN` уже загружены из приватной конфигурации в окружение.

```powershell
$telegramApi = "https://api.telegram.org/bot$env:BOT_TOKEN"
$body = @{
    url = "https://api.cheremha.ru/channels/telegram/webhook"
    secret_token = $env:TELEGRAM_WEBHOOK_SECRET_TOKEN
    max_connections = 1
    allowed_updates = @("message")
    drop_pending_updates = $false
} | ConvertTo-Json -Compress
Invoke-RestMethod "$telegramApi/setWebhook" -Method Post -ContentType "application/json" -Body $body
Invoke-RestMethod "$telegramApi/getWebhookInfo"
```

Откройте ссылку-приглашение в тестовом боте. После подтверждения доступа задайте вопрос и отправьте уточнение до готового ответа. После перезапуска Flue убедитесь, что контекст сохраняется. `/reset` открывает диалог с чистым контекстом.

После проверки остановите прежний polling основного бота и зарегистрируйте webhook для его токена. Для отката остановите Flue, вызовите `deleteWebhook` с `drop_pending_updates=false` и запустите предыдущую версию с её БД. Telegram позволяет использовать один способ получения апдейтов на токен.

## База документации

Очередь RAG различает источники `file`, `url` и `confluence`. Для файла оригинал
определяется по `file_id` в file-service, для прямой ссылки используется `source_url`.
Confluence хранит идентификаторы пространства и страницы в `source_locator`,
а номер публикации в `source_revision`.

В Telegram работает один бот через агент `Bars` и тулзу `answer_from_docs`.
Внутренний агент Flue `DocumentImport` читает изображения и делит текст при загрузке документа.
Вход импорта и найденные для ответа фрагменты обрабатываются в памяти. История Telegram
сохраняет готовые ответы с выбранными цитатами.
Тулза ищет фрагменты через FastAPI, выбирает ответ и цитаты одним вызовом модели Flue,
затем сверяет идентификаторы источников и точный текст цитат.
FastAPI строит эмбеддинги Qwen3 Embedding 8B через `EMBEDDING_BASE_URL` и
`EMBEDDING_API_KEY` и хранит фрагменты в Qdrant. Для OpenRouter задайте
`EMBEDDING_BASE_URL=https://openrouter.ai/api/v1`. API добавляет путь `/embeddings`.
Flue берёт адрес и ключ для чата и Vision из `CHAT_BASE_URL` и `CHAT_API_KEY`.
В Telegram тулза доступна зарегистрированным сотрудникам.

- `POST /rag/documents` принимает multipart с обязательным `file` и необязательными
  `title` и `source_id`. API сначала сохраняет оригинал в file-service и только после этого
  создаёт задание импорта. Ответ `202` содержит `job_id`, `source_id` и `file_id`.
  Если название пропущено, используется имя файла. При сбое записи задания после загрузки
  оригинал может остаться в file-service без задания импорта.
- `POST /rag/documents/from-url` принимает JSON с обязательным `url` и необязательными
  `title` и `source_id`. Ответ `202` содержит `job_id` и `source_id`. Воркер скачивает
  документ по публичной прямой ссылке. Обе формы поддерживают PDF, DOCX и Markdown в UTF-8
  размером до 25 МиБ.
  Из PDF и DOCX извлекаются встроенные изображения, из Markdown — встроенные изображения
  в формате data URI. Обычные ссылки на изображения остаются частью текста.
- `GET /rag/jobs?page=1&page_size=20` возвращает `items`, `total`, `page` и `page_size`.
  Для таблицы возвращается последнее задание по каждому `source_id`, новые загрузки первыми.
  `include_history=true` включает все отдельные задания. В строке есть `id` задания, `title`, `format`,
  `size_bytes`, `created_at`, `status`, `error_code`, `has_active_version` и `document_url`.
  Для загруженного файла `document_url` содержит подписанную ссылку на файл из этой записи,
  в том числе при ошибке обработки, для URL-импорта — адрес
  источника. У старых записей без оригинала и адреса значение `null`. Для ранее
  загруженных файлов размер может быть `null`; у URL-импорта до успешной обработки `format`
  может быть `url`. Если обновление завершилось ошибкой, `has_active_version` показывает,
  доступна ли боту предыдущая версия.
- `GET /rag/jobs/{job_id}` возвращает статус, ошибку или число опубликованных фрагментов.
  Для обновления передайте прежний `source_id`. После успешного импорта поиск переключается
  на новую версию. Старые фрагменты удаляются из Qdrant при очередной очистке через две минуты
  или позже. При ошибке импорта по-прежнему доступна предыдущая версия. Обе формы загрузки и
  ручка статуса требуют JWT админки.
- `PUT /rag/jobs/{job_id}` принимает multipart с `file` и необязательным `title`.
  Ответ `202` сохраняет `job_id` и `source_id`, возвращает новый `file_id`.
  Существующее задание снова переходит в очередь.
  Бот продолжает использовать текущую версию до успешного завершения замены.
- `DELETE /rag/jobs/{job_id}` удаляет задания источника вместе с его активной версией.
  После `204` источник исчезает из списка и поиска, подписанные ссылки перестают открываться.
  Воркер удаляет фрагменты и файлы в фоне. Данные для повтора очистки хранятся в `rag_jobs.cleanup`,
  а запись задания удаляется после очистки. Внешний документ остаётся у владельца URL.
  Обе операции требуют JWT админки. Для очистки оригиналов одновременно обновите API и file-service.
- `GET /file-service/{file_id}?sig=…` открывает конкретный оригинал через FastAPI и file-service.
  Файл доступен тому, у кого есть подписанная ссылка из ответа бота. При смене `BOT_API_TOKEN`
  подписи в уже отправленных ссылках перестают действовать. Для внешнего URL в источнике
  используется исходный адрес. Если владелец заменит документ по этому адресу, старое
  сообщение откроет текущий файл по ссылке.
- `POST /internal/rag/search` принимает `question`, `original_question` и необязательные
  `exact_id` и `standalone`. Возвращает фрагменты для тулзы и требует `X-Bot-Token: <BOT_API_TOKEN>`.

Поиск кэширует непустые результаты в отдельном `redis-rag` на 24 часа с момента записи.
Ключ зависит от запроса и активных версий документов. Как только версия опубликована или источник
удалён, новые запросы используют актуальный набор версий. При недоступности кэша поиск идёт в Qdrant.
Модель Flue приводит разные формулировки к короткому поисковому запросу с теми же условиями. Для
самостоятельных вопросов API также связывает исходный текст с записью кэша. Уточнения по истории
и части составного вопроса используют ключ поискового запроса.
При достижении `RAG_REDIS_MAXMEMORY` (по умолчанию `64mb`) Redis вытесняет редко используемые записи
через `allkeys-lfu`. Для локального запуска выполните `docker compose -p bars-dev -f docker-compose-dev.yml up -d redis-rag`.
Адрес подключения меняется через `RAG_REDIS_URL`, локальный порт — через `RAG_REDIS_PORT`.

## Проверки разработки

После `npm ci` в `flue/` выполните `npm run typecheck` и `npm run build`.

Процесс Flue рассчитан на одну реплику. Сбой между отправкой в Telegram и подтверждением результата в БД переводит отправку в состояние `unknown`. Запись доступна в `bars_telegram_deliveries`. Такие отправки требуют проверки по журналу и чату, поскольку автоматический повтор может отправить сообщение второй раз.
