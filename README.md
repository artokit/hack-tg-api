# Telegram-агент БАРС

Flue принимает Telegram webhook, вызывает OpenAI-совместимую модель и хранит диалоги в PostgreSQL. FastAPI обслуживает авторизацию и управление сотрудниками. Простой текст в личном чате идёт агенту. Команды `/start` и `/reset` работают без модели. `/reset` открывает новый диалог, предыдущий сохраняется в PostgreSQL.

## Запуск

### Локальная разработка

`docker-compose-dev.yml` поднимает PostgreSQL 17 с базой `hackathon`, Redis, Flue, внутренний API для вложений Jira, файловый сервис, отдельную БД файлового сервиса и MinIO. Основной API запускается локально. Flue обращается к нему через `host.docker.internal:8000` (порт задаётся через `API_PORT`), к внутреннему API — через `http://internal-api:8000`.

В корневом `.env` задайте `FILE_DB_PASSWORD` и `MINIO_ROOT_PASSWORD` разными случайными значениями от 32 символов. Остальные настройки файлового сервиса доступны в `.env.example`.

Для Flue в корневом `.env` также заполните `BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET_TOKEN`, `BOT_API_TOKEN`, `CHAT_BASE_URL`, `CHAT_MODEL` и при необходимости `CHAT_API_KEY`. Значение `BOT_API_TOKEN` должно совпадать с настройкой локального API. Если модель работает на этом же компьютере, используйте в `CHAT_BASE_URL` адрес `host.docker.internal`, не `localhost` и не адрес FastAPI.

Из корня проекта:

```powershell
docker compose -f docker-compose-dev.yml up -d --build --wait
```

Для локального API в `api/.env` задайте `DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/hackathon` и `REDIS_URL=redis://127.0.0.1:6379/0`, а также секреты приложения. Если меняли `POSTGRES_PORT` или `REDIS_PORT`, укажите те же порты в URL. Переменные текущего терминала имеют приоритет над `.env`.

```powershell
cd api
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn main:app --host 0.0.0.0 --reload
```

Адреса по умолчанию: API — `http://127.0.0.1:8000/docs`, внутренний API — `http://127.0.0.1:8001/docs`, Flue — `http://127.0.0.1:3000/health`, файловый сервис — `http://127.0.0.1:8080/file-service/docs`, MinIO Console — `http://127.0.0.1:9001`. Внутренний API в dev-compose опубликован только на loopback; его порт задаётся через `INTERNAL_API_PORT`. Миграции файлового сервиса и создание bucket выполняются при старте его контейнера; миграции основного API применяются командой выше. Основной API слушает `0.0.0.0` для доступа из контейнера Flue; ограничьте входящий доступ средствами брандмауэра.

Не запускайте dev-compose и полный Compose одновременно на одинаковых портах. Их основные PostgreSQL используют разные версии, базы и volumes; данные автоматически не переносятся. Не меняйте версию PostgreSQL для существующего volume и не удаляйте volumes для перезапуска.

### Полный запуск в Docker

1. Скопируйте `.env.example` в `.env`. Укажите токен бота в `BOT_TOKEN`, произвольный независимый `TELEGRAM_WEBHOOK_SECRET_TOKEN` и настройки модели. `CHAT_BASE_URL` — базовый URL совместимого API, например `https://provider.example/v1`. При работе без авторизации оставьте `CHAT_API_KEY` пустым.
2. Выполните `docker compose up -d --build --wait`. FastAPI применит миграции, Flue создаст таблицы агента и обработки Telegram. Новый volume называется `bars-hackathon_postgres_flue_data`. Volume прежнего Python-бота можно сохранить для отката.
3. Проверьте `http://127.0.0.1:3000/health` с хоста. FastAPI доступен внутри Compose по адресу `http://api:8000`. Для второго экземпляра используйте другое имя проекта Compose, другие хостовые порты и отдельный тестовый токен.

## Файловый сервис и MinIO

Добавьте в корневой `.env`:

```dotenv
FILE_SERVICE_PORT=8080
FILE_DB_USER=file_service
FILE_DB_PASSWORD=replace-with-a-long-random-database-password
FILE_DB_NAME=files
MINIO_ROOT_USER=file_storage_admin
MINIO_ROOT_PASSWORD=replace-with-another-long-random-storage-password
MINIO_API_PORT=9000
MINIO_CONSOLE_PORT=9001
S3_BUCKET_NAME=files
```

Замените оба пароля разными случайными значениями, желательно от 32 символов; MinIO требует минимум 8 символов. Остальные значения можно оставить как в примере. Для генерации пароля можно выполнить `python -c "import secrets; print(secrets.token_urlsafe(32))"`. В Docker Compose отдельный `file-service/.env` не нужен: `DB_*` и `S3_*` передаются сервису из корневых настроек автоматически.

Запуск только файлового контура: `docker compose up -d --build --wait file-service`. PostgreSQL файлового сервиса и MinIO поднимутся как зависимости. File-service сначала применяет свои миграции через asyncpg, затем создаёт отсутствующий bucket и запускает HTTP-сервер.

- File-service: `http://127.0.0.1:8080/file-service/docs`.
- S3 API MinIO: `http://127.0.0.1:9000`.
- Консоль MinIO: `http://127.0.0.1:9001`, вход по `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`.
- Внутри Compose file-service доступен по `http://file-service:3000`, а MinIO — по `http://minio:9000`.

Метаданные файлов хранятся в отдельном PostgreSQL и volume `file_postgres_data`, объекты — в `minio_data`. Миграции файлового сервиса не затрагивают БД основного API. Порты проброшены только на `127.0.0.1` и могут быть изменены переменными из примера.

Bucket по умолчанию приватный. Текущий file-service возвращает в поле `url` внутренний S3-адрес, а не публичную или подписанную ссылку; для доступа к объектам нужны S3-учётные данные либо вход в консоль MinIO.

Готовые официальные образы MinIO недоступны в проверенных реестрах. Используется community-сборка `netvark/minio` с открытым процессом сборки, закреплённая по digest `sha256:77281ea99af0d02e2880e91d345bf81cae584454aedffbb7912331774f42d4bf`. Community-версия MinIO больше не поддерживается: этот контур предназначен для локальной разработки, а для публичного production-хранилища нужен поддерживаемый S3-сервис.

## Документация API

Swagger UI доступен на `http://127.0.0.1:8000/docs`, схема OpenAPI — на `http://127.0.0.1:8000/openapi.json`. В Swagger можно посмотреть и вызвать ручки входа, сотрудников, приглашений и проверки состояния API. Порт API в Docker Compose можно изменить через `API_PORT` в `.env`; доступ с хоста открыт только на `127.0.0.1`.

## Вложения к заявкам Jira

Настройки Jira читаются сервером из окружения и `.env`. Для локального основного API их можно задать в `api/.env`. Внутренний API запускается в Docker, поэтому для него в обоих вариантах Compose задайте настройки в корневом `.env`:

```dotenv
JIRA_BASE_URL=https://your-company.atlassian.net
JIRA_EMAIL=integration@example.com
JIRA_API_TOKEN=
JSM_SERVICE_DESK_ID=1
JSM_REQUEST_TYPE_ID=1
```

Замените адрес, email и ID на свои значения. Если одни и те же настройки указаны в обоих `.env`, корневой файл имеет приоритет; переменные окружения имеют приоритет над файлами. После изменения настроек пересоздайте `internal-api` через `docker compose -f docker-compose-dev.yml up -d --build --wait internal-api` для разработки или `docker compose up -d --build --wait internal-api` для полного Compose. Локальный основной API перезапустите отдельно.

Для Jira Cloud API-токен создаётся в аккаунте Atlassian: https://id.atlassian.com/manage-profile/security/api-tokens → Create API token → имя и срок действия → Create → Copy. `JIRA_EMAIL` должен принадлежать владельцу токена. Для адреса `https://your-company.atlassian.net` используется токен без scopes. Для токена со scopes нужен `JIRA_BASE_URL=https://api.atlassian.com/ex/jira/<cloudId>` и права на чтение заявок, создание заявок и прикрепление файлов. Права учётной записи на проект JSM также обязательны. Это настройка Jira Cloud; Jira Data Center использует другой способ выдачи и применения токенов.

`JIRA_API_TOKEN` не передаётся клиентом нашего API: адаптер использует его вместе с `JIRA_EMAIL` для Basic Auth при обращении к Jira. Для ручки вложений `BOT_API_TOKEN`, JWT и `X-Bot-Token` не нужны. `BOT_API_TOKEN` остаётся нужен для существующих ручек сотрудников и приглашений. Не публикуйте токены и не добавляйте `.env` в git.

`POST /private/tickets/{ticket_id}/attachments` прикрепляет один файл к заявке, созданной через `POST /tickets`. В адресе передаётся локальный `tickets.id`, API сам находит заявку Jira по сохранённым `external_id`/`external_key`. Ручка зарегистрирована только в `api/internal.py`; основной `main:app` на порту 8000 её не обслуживает.

`POST /tickets` при создании заявки сохраняет из ответа Jira внешний ID (`issueId`) и ключ (`issueKey`), возвращает их в полях `external_id` и `external_key`. Заявки, созданные до этой правки, полей не имеют: для них вложения вернут `400`, нужна новая заявка.

В полном Compose сервис `internal-api` не публикует порт на хост. Вызовы доступны из доверенной Docker-сети по адресу `http://internal-api:8000/private/tickets/{ticket_id}/attachments`; Flue получает базовый адрес в `INTERNAL_API_URL`. Не проксируйте этот сервис наружу и не добавляйте публичный проброс порта: защита ручки основана на сетевой изоляции, а не на префиксе `/private`.

Для ручной проверки в dev-compose откройте `http://127.0.0.1:8001/docs`: авторизация не требуется. Пример запроса с компьютера разработчика:

Тело запроса — `multipart/form-data`: обязательное поле `file` и необязательное `public` (по умолчанию `false`, вложение доступно только сотрудникам поддержки). Для внутреннего вложения учётной записи интеграции нужны права агента JSM. `public=true` делает вложение доступным клиенту. Размер файла — от 1 байта до 10 МиБ; ограничения самой Jira также применяются.

```powershell
curl.exe -X POST "http://127.0.0.1:8001/private/tickets/2/attachments" -F "file=@conversation.txt" -F "public=false"
```

При успехе API возвращает `201` с полями `issue_id_or_key` (ключ заявки Jira), `comment_id`, `filename`, `public`. Ошибки: `400` — некорректный или пустой файл, отказ Jira по входным данным или у заявки нет привязки к Jira; `404` — заявки нет в нашей БД либо заявка/сервис-деск не найдены в Jira; `413` — превышение размера; `422` — неверный ID либо формат формы; `502` — транспортная ошибка, некорректный ответ или другая ошибка Jira.

Эндпоинт не создаёт тикет и не меняет локальную БД. Повторная успешная отправка добавляет новое вложение. При тайм-ауте результат может быть неизвестен: перед повтором проверьте вложения в Jira.

## Авторизация администратора

Задайте случайный `JWT_SECRET` длиной не менее 32 символов в `.env`. Секрет должен оставаться одинаковым между перезапусками и экземплярами API. Срок действия JWT задаётся через `JWT_ACCESS_TOKEN_EXPIRE_MINUTES` и по умолчанию составляет 60 минут.

Миграция `0004` создаёт администратора `admin@example.com` с временным паролем `admin`. Миграция `0005` удаляет старых Telegram-пользователей, тикеты и сообщения тикетов, а таблицу `admins` переименовывает в `users`, сохраняя аккаунты для входа. Удалённые данные при откате не восстанавливаются. В БД хранится только bcrypt-хеш пароля. Эти реквизиты предназначены только для разработки.

`POST /auth/login` принимает JSON с полями `email` и `password` и возвращает `access_token` и `token_type: "bearer"`. Регистрации и обновления токена нет. Для всех ручек `/employees` передавайте заголовок `Authorization: Bearer <access_token>`. Без действующего токена API возвращает `401`. В Swagger нажмите **Authorize** и вставьте полученный токен без префикса `Bearer`.

## Кэш сотрудников и отзыв доступа

Проверочные ручки сотрудников сохраняют прежние адреса и авторизацию. При поиске по `telegram_id` API сначала читает Redis. Если записи нет, API обращается в PostgreSQL и кэширует только найденного сотрудника на 180 секунд. Чтение не продлевает TTL. Отсутствующий сотрудник не кэшируется: API возвращает `404`, бот сообщает об отсутствии доступа.

`DELETE /employees/{employee_id}` требует JWT, очищает кэш и удаляет сотрудника из PostgreSQL; успех — `204`, неизвестный UUID — `404`. Заполнение кэша и удаление синхронизируются по `telegram_id`, чтобы параллельная проверка не восстановила запись после удаления. После успешного удаления следующая проверка бота отказывает в доступе. При недоступном Redis проверка и удаление возвращают `503`, а не предоставляют доступ по умолчанию.

Удалять сотрудника нужно через API. Прямое удаление SQL-запросом не очищает Redis: такая запись останется до истечения TTL.

В Docker Compose Redis запускается автоматически. Для локальной разработки выполните `docker compose -f docker-compose-dev.yml up -d redis`; API по умолчанию использует `redis://127.0.0.1:6379/0`. Другой адрес можно задать через `REDIS_URL`; порт Redis в dev-compose — через `REDIS_PORT`.

## Данные сотрудника из Telegram

Миграция `0008` добавляет `employees.is_parsed` со значением `false` по умолчанию, в том числе для существующих сотрудников. `POST /employees` создаёт сотрудника с `is_parsed: false`. При первом сообщении бот читает этот флаг и, если данные ещё не получены, вызывает `PATCH /private/employees/by-telegram-id/{telegram_id}` с `X-Bot-Token`.

PATCH принимает три обязательных nullable-поля: `username`, `first_name`, `last_name`. Он сохраняет полученные значения и устанавливает `is_parsed: true`, даже если все значения — `null`. В ответе — обновлённый `EmployeeRead`. Неизвестный сотрудник — `404`. Повторный PATCH уже обработанного сотрудника возвращает текущие данные без перезаписи. Кэш Redis обновляется сразу, без ожидания истечения TTL. Сведения не запрашиваются у пользователя вручную.

## Приглашения сотрудников

Укажите `TELEGRAM_BOT_USERNAME` без `@` и задайте независимый случайный `BOT_API_TOKEN` длиной не менее 32 символов в `.env`. API и Flue должны использовать одинаковый `BOT_API_TOKEN`. Для локального запуска Flue также задайте `API_URL`, например `http://127.0.0.1:8000`; в Docker Compose адрес уже настроен.

Все ручки `/invites` требуют JWT:

- `POST /invites` — создать приглашение и получить `link` вида `https://t.me/<bot_username>?start=invite_<id>`. Тело: `count_of_use` (по умолчанию 1), необязательные `first_name` и `last_name`. ФИ разрешено только для одноразового приглашения. Без `TELEGRAM_BOT_USERNAME` ручка возвращает `503` и не создаёт запись.
- `GET /invites?page=1&page_size=20` — список действующих приглашений, размер страницы до 100.
- `GET /invites/{id}` — получить приглашение и оставшееся число использований.
- `DELETE /invites/{id}` — отозвать приглашение, ответ `204`.

После `/start invite_<id>` или `/start <id>` бот сразу вызывает `POST /private/invites/{id}/accept`, передавая `telegram_id`, `username`, `first_name` и `last_name` из данных Telegram; отсутствующие значения передаются как `null`. Сотрудник создаётся сразу с `is_parsed: true`. Вводить имя и фамилию не нужно. При `201` бот подтверждает доступ. Уже добавленный сотрудник получает подтверждение без повторного использования инвайта. При ошибке активации бот сообщает об отказе.

На каждом сообщении бот обращается к `GET /private/employees/by-telegram-id/{telegram_id}`. Он передаёт `X-Bot-Token` в приватные ручки сотрудников и приглашений основного API. Отдельный внутренний API вложений не требует этого заголовка. Запросы к агенту доступны только действующим сотрудникам.

ФИ из персонального приглашения имеет приоритет над данными Telegram. После создания сотрудника число использований уменьшается; последнее использование удаляет приглашение. Создание сотрудника и списание выполняются отдельными сохранениями без общей транзакции и блокировок: при параллельных запросах или сбое между сохранениями возможна рассинхронизация.

## Публичный webhook

Для примера используем `bars-bot.cheremha.ru`. Создайте A-запись `bars-bot` на публичный IPv4 хоста с Compose. Настройте сертификат Let's Encrypt в существующем HTTPS-сервере. Пример маршрута для Nginx внутри HTTPS-блока этого поддомена.

```nginx
location = /channels/telegram/webhook {
    limit_except POST { deny all; }
    proxy_pass http://127.0.0.1:3000;
}

location / {
    return 404;
}
```

На тестовом токене проверьте доступность TLS и зарегистрируйте webhook. Следующий пример PowerShell предполагает, что `BOT_TOKEN` и `TELEGRAM_WEBHOOK_SECRET_TOKEN` уже загружены из приватной конфигурации в окружение.

```powershell
$telegramApi = "https://api.telegram.org/bot$env:BOT_TOKEN"
$body = @{
    url = "https://bars-bot.cheremha.ru/channels/telegram/webhook"
    secret_token = $env:TELEGRAM_WEBHOOK_SECRET_TOKEN
    max_connections = 1
    allowed_updates = @("message")
    drop_pending_updates = $false
} | ConvertTo-Json -Compress
Invoke-RestMethod "$telegramApi/setWebhook" -Method Post -ContentType "application/json" -Body $body
Invoke-RestMethod "$telegramApi/getWebhookInfo"
```

Откройте ссылку-приглашение в тестовом боте. После подтверждения доступа задайте вопрос и отправьте уточнение до готового ответа. После перезапуска Flue убедитесь, что контекст сохраняется. `/reset` открывает диалог с чистым контекстом.

После проверки остановите прежний polling основного бота и зарегистрируйте webhook для его токена. Для отката остановите Flue, вызовите `deleteWebhook` с `drop_pending_updates=false` и запустите предыдущую версию с её БД. Telegram позволяет использовать один способ получения апдейтов на токен.

## Проверки разработки

После `npm ci` в `flue/` выполните `npm run typecheck` и `npm run build`.

Процесс Flue рассчитан на одну реплику. Сбой между отправкой в Telegram и подтверждением результата в БД переводит отправку в состояние `unknown`. Запись доступна в `bars_telegram_deliveries`. Такие отправки требуют проверки по журналу и чату, поскольку автоматический повтор может отправить сообщение второй раз.
