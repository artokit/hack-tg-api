# Правила для агентов (OpenCode / Claude Code / и т.п.)

## Общие принципы

1. **Следуй текущей архитектуре проекта.** Перед написанием кода изучи структуру проекта и уже существующие файлы. Новый код должен вписываться в существующие паттерны, а не изобретать свои.

2. **Не сваливай всё в один файл.** Код должен лежать там, где ему место по структуре проекта. Перед созданием нового файла убедись, что нет подходящего существующего.

3. **Переиспользуй существующий код.** Если в проекте уже есть похожая функция/клавиатура/обработчик — используй или расширяй её, а не пиши дубликат.

## Структура проекта

```
hackathon/
├── api/          # FastAPI backend — архитектура onion
│   ├── main.py           # ТОЛЬКО сборка приложения: создание FastAPI + include роутеров
│   ├── routes/           # хэндлеры FastAPI (APIRouter): HTTP-валидация, вызов services
│   ├── schemas/          # pydantic DTO (*Create/*Read) — вход/выход эндпоинтов
│   ├── services/         # бизнес-логика (use cases), работает через repositories
│   ├── repositories/     # доступ к данным: SQLAlchemy-запросы, commit, возврат ORM-моделей
│   ├── models/           # доменные сущности (зарезервировано; пока ORM-модели в db/models.py)
│   ├── db/               # движок, сессии, Base, ORM-модели (SQLAlchemy)
│   ├── alembic/          # миграции
│   ├── utils/            # вспомогательные функции
│   └── agents/           # зарезервировано
└── telegram-bot/ # Aiogram бот
    ├── main.py           # точка входа, регистрация роутеров
    ├── config.py
    ├── http_client.py    # generic HTTP-клиент на httpx: Result[T] (status_code + распарсенная модель T)
    ├── routers/          # хэндлеры aiogram (Router). Каждый домен — свой файл
    ├── keyboards/        # клавиатуры. Каждый файл — функция-фабрика вида get_*_keyboard()
    ├── states/           # FSM-состояния (StatesGroup)
    ├── models/           # pydantic-модели ответов API (DTO для парсинга JSON)
    └── services/         # обёртки над API через HttpClient, без прямого доступа к БД
```

## Правила для telegram-бота (aiogram)

1. **Все клавиатуры — только в папке `keyboards/`.**
   - Клавиатура собирается в отдельной функции-фабрике с именем `get_*_keyboard()`.
   - Стиль — как в `keyboards/start.py`: `InlineKeyboardMarkup(inline_keyboard=[[InlineKeyboardButton(...)]])`.
   - В хэндлерах (`routers/`) клавиатуры inline **не собираются** — только вызов функции из `keyboards/`.
   - Пример подключения: `from keyboards import ask as ask_keyboard` → `reply_markup=ask_keyboard.get_operator_keyboard()`.

2. **Хэндлеры — только в `routers/`.**
   - Хэндлер для нового домена = новый файл `routers/<domain>.py` с `router = Router()`.
   - Не пиши хэндлеры в `main.py`, `keyboards/`, `states/` или где-либо ещё.

3. **Роутеры регистрируются в `main.py` через `dp.include_router(...)` в порядке приоритета.**
   - Роутер, который ловит сообщения по состоянию FSM (или «ловушка на все сообщения»), подключается **последним**.

4. **FSM-состояния — только в `states/`** (один файл на домен, `StatesGroup`).

5. **Хэндлеры по сообщению обязаны иметь фильтр состояния**, если срабатывание должно быть только в определённом FSM-состоянии:
   ```python
   @router.message(AskStates.user_ask)   # правильно
   @router.message()                     # ловушка на ВСЕ сообщения — только осознанно, как fallback
   ```

## Взаимодействие с БД — только через API

1. **Бот никогда не обращается к БД напрямую.** Никаких импортов SQLAlchemy/alembic из `api/` в `telegram-bot/` и наоборот. Любые данные читаются и пишутся только HTTP-запросами к API.
2. **API — единственная точка доступа к БД.** SQLAlchemy-модели, сессии и запросы живут только в `api/`.
3. **Все обращения к API — только через `HttpClient` из `http_client.py`.** Прямое использование `httpx.AsyncClient` в сервисах и хэндлерах запрещено. Паттерн: `HttpClient.get/post(path, ResponseModel) -> Result[T]`, где `Result` содержит `status_code` и распарсенную в pydantic-модель данные (`data: T`). Сервис проверяет `status_code` (404 → `None` и т.п.) и отдаёт вызывающему коду готовую модель из `models/`, а не сырой json.
4. **User в БД** пока содержит: `id`, `telegram_user_id` (уникальный), `username` (nullable).
5. **Раздельные ручки на создание и чтение.** `POST /users` только создаёт (409, если пользователь с таким `telegram_user_id` уже существует). Проверка существования — через `GET /users/by-telegram-id/{telegram_user_id}` (404, если нет). Бот при `/start` сначала проверяет через GET и создаёт только если пользователя нет — повторный `/start` не дублирует его.

## Архитектура API — onion (луковичная)

**БД — только PostgreSQL.** Никакого sqlite нигде: ни в коде, ни в миграциях, ни в тестах. Драйвер — `asyncpg`. Строка подключения — из `DATABASE_URL` в `api/.env` (формат: `postgresql+asyncpg://user:password@host:5432/dbname`). Миграции тоже идут в postgres через `DATABASE_URL` (см. `alembic/env.py`). Локальный postgres для разработки поднимается через `docker compose -f docker-compose-dev.yml up -d` (только postgres, без API/бота).

Направление зависимостей — снаружи внутрь, внутренние слои не знают о внешних:

```
routes → services → repositories → db
   ↕ DTO через schemas
```

1. **Хэндлеры (эндпоинты) — только в `routes/`.** `main.py` не содержит хэндлеров — только создание `FastAPI` и `app.include_router(...)`. Хэндлер делает: валидацию входа (schemas), вызов service, HTTP-статусы (404 и т.п.). Никакой бизнес-логики и SQL в хэндлерах.
2. **DTO (pydantic-модели запросов/ответов) — только в `schemas/`.** Классы вида `*Create`/`*Read` (`UserCreate`, `UserRead`). Нигде кроме `schemas/` pydantic-модели API не объявляются.
3. **Бизнес-логика — только в `services/`** (use cases, условия, идемпотентность). Сервис получает `UserCreate`, работает через repository, возвращает доменный объект.
4. **SQLAlchemy-запросы и `commit` — только в `repositories/`.** Routes и services сессию напрямую не используют — сессия прокидывается в репозиторий. Репозиторий возвращает ORM-модели из `db/models.py`.
5. **Направление импортов строго внутрь:** `routes → services → repositories → db`. Репозиторий не импортирует `schemas`/`fastapi`; сервис не импортирует `fastapi`. Композиция (создание `Repository(session)` → `Service(repo)`) — через `Depends`.
6. **Провайдеры зависимостей — в отдельном файле `api/depends.py`.** Функции вида `get_user_service(session = Depends(get_async_session))`, собирающие сервисы из репозиториев и сессий, объявляются там и импортируются в роутерах (`from depends import get_user_service`). В `routes/` зависимости inline не собираются.
7. **Один домен = один файл в каждом слое:** `routes/users.py`, `schemas/users.py`, `services/users.py`, `repositories/users.py`. Новый домен — новый набор файлов, а не свалка в существующих.
8. **SQLAlchemy-модели — в `db/models.py`** (там их ищет alembic: `from db import models`), pydantic DTO — в `schemas/`, не путать.
9. Миграции — через alembic (`api/alembic/versions/`), менять схему руками в БД нельзя.
10. **Ручки разделены по операциям, идемпотентность — не в API.** `POST /users` только создаёт: если пользователь с таким `telegram_user_id` уже есть — `409 Conflict`. Поиск по `telegram_user_id` — отдельная ручка `GET /users/by-telegram-id/{telegram_user_id}` (404, если нет). Никаких «создать-или-вернуть-существующего» комбинированных ручек. Дедупликация — на стороне вызывающего (бот): сначала проверить через GET, создавать только если 404. Новые сущности делай по тому же принципу: раздельные ручки на создание и чтение.

## Стиль кода

1. **Никогда не пиши комментарии и докстринги сам.** Они бесполезны — код должен говорить сам за себя. Писать комментарий/докстринг только если пользователь явно попросил это.
2. Комментарии (если пользователь попросил) и тексты сообщений бота — на русском, идентификаторы — на английском.
3. Импорты — только то, что реально используется.
4. Перед коммитом убедись, что код запускается: нет синтаксических ошибок (пустые `reply_markup=` и т.п. недопустимы).
