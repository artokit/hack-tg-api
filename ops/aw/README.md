# AW: аналитика реальных обращений

Источник `Bars_Hakaton` читает PostgreSQL сервера. Модель «БАРС — обращения (реальные данные)» обновляется каждые 15 минут. SQL блока `support_requests_safe` хранится в [requests.sql](requests.sql), а не только в интерфейсе AW.

Панель: https://aw-demo.ru/app/dashboard/update/25878

## Что сохраняет бот

У успешно отправленных сообщений в `bars_telegram_request_events` записываются два независимых признака:

- `has_answer`: в сообщении есть содержательный ответ по документации с источниками либо ответ по присланному вложению;
- `has_clarification`: в сообщении есть уточняющий вопрос или запрос продолжения диалога.

Тип ответа (`response_type`) не добавляется. Новых таблиц для этих признаков нет. `UNIQUE(request_id, event_key)` сохраняет идемпотентность: повторная обработка одной доставки не увеличивает число ответов.

Признаки определяются по реально сформированному сообщению. Если частичный ответ и уточнение отправляются отдельно, первое сообщение имеет `has_answer = true`, второе — `has_clarification = true`. Если оба содержатся в одном сообщении, оба признака равны `true`. Приветствия, благодарности, вопросы об оценке, уведомления о закрытии и технические ошибки не считаются содержательными ответами. Запросы дополнительных деталей, подтверждения передачи специалисту и подтверждения продолжения/закрытия диалога консервативно учитываются как уточнения. Обычная просьба оценить ответ — нет.

Событие добавляется только после доставки со статусом `sent`. Повторно прочитанная успешная доставка использует прежний ключ события. Неудачные и неизвестные доставки не создают успешного события ответа. Несколько физических частей длинного Telegram-сообщения считаются одним логическим ответом.

Новые обращения получают `tracks_response_metrics = true` в `bars_telegram_requests`. У существовавших до обновления обращений маркер остаётся `false`, в том числе если они были открыты во время выкладки. Он не включается при очередном сообщении уже существующего обращения.

## Категории

Классификатор уже включён в финализацию закрытого обращения: `agents/support-request-finalizer.ts` вызывает `classifySupportRequest`, затем `support-api.ts` передаёт результат в `POST /private/support-requests`. API валидирует категории и сохраняет `category_id`.

Текущий список: `access`, `navigation`, `search_filters`, `documents_records`, `business_processes`, `employees_contacts`, `other`. AW переводит эти ID в русские названия. `deals_budget` в текущем контракте отсутствует. Старые записи с пустой категорией автоматически не переклассифицируются; открытые обращения ещё не прошли классификацию. Для них остаётся «Тема не указана». При ошибке классификации приложение использует `other`.

## SQL и правила расчёта

SQL объединяет `support_requests` и `bars_telegram_requests` по ID, поэтому учитывает как сохранённые результаты, так и открытые/ожидающие финализации обращения. События агрегируются до одной строки на обращение до соединения: несколько сообщений не умножают количество обращений. Категория из сохранённого результата имеет приоритет.

Тексты вопросов, ответов, содержимое `handoff`, имена, Telegram ID и промпты не входят в результат запроса. `to_jsonb` используется внутри PostgreSQL только для безопасного чтения необязательных полей метаданных до выкладки миграции; полные записи не экспортируются.

1. **Без оператора, %**: `AVG(bot_resolved_percent)`. Требуются `is_resolved = true`, `close_reason = confirmed` и отсутствие `handoff`. Знаменатель — все обращения, включая открытые. `thanks` и неизвестный результат не считаются `confirmed`.
2. **Причины эскалаций**: группировка по `close_reason_label`, `SUM(request_count)`, исключаются `confirmed`, `spam` и `reset`. По согласованному правилу включаются таймауты. `spam` остаётся в БД и остальных показателях, но не попадает в эту диаграмму. Открытые обращения без причины не включаются. Это не равно числу успешно доставленных оператору тикетов.
3. **Решено с первого ответа, %**: `AVG(first_answer_resolved_percent)`. Успех — подтверждённое решение без `handoff`, ровно один содержательный ответ, ни одного уточнения. История пригодна только при маркере полного учёта и отсутствии нетипизированных событий ассистента. Для остальных обращений значение `NULL`, а не `0`. Открытые пригодные обращения входят в знаменатель. Рядом показывается `AVG(response_metrics_coverage_percent)` — доля всех обращений с полным учётом.
4. **Темы, требующие оператора**: по `topic` показываются `SUM(request_count)`, `SUM(escalation_count)`, `AVG(escalation_percent)`. Признак передачи — блок `handoff` в результате или событие `handoff:`; это не подтверждает успешную доставку оператору. Высокая доля передач не доказывает принципиальную нерешаемость темы ботом.

Для KPI используется одна техническая группа `request_count` (в каждой строке равна 1). Это заставляет AW применить агрегацию по всей выборке, а не вывести первое значение. Нельзя усреднять уже агрегированные проценты разных дней/тем без их знаменателей.

## Развёртывание

Используйте изменения от актуального `master`. В этой цепочке `0016` уже занята таблицей `support_requests`, `0023` — журналом импорта документов, `0024` — сроком действия приглашений. Ранее подготовленную в старой ветке `0016_remove_aw_mock_source.py` сюда переносить нельзя. Актуальные AW-миграции: `0025` — признаки ответов, `0026` — удаление моков, `0027` — удаление `reset`. Старые неприменённые варианты AW-миграций из промежуточных коммитов не выкладывайте.

1. Сделайте резервную копию БД.
2. Выложите изменения. Примените API-миграции, затем запустите новый Flue:

```sh
docker compose stop flue
docker compose up -d --build --wait api
docker compose up -d --build --wait flue
```

При локальном запуске миграции выполняются из `api` командой `python -m alembic upgrade head`. Нельзя запускать новый обработчик поверх старой схемы.

Миграция `0025` добавляет признаки к уже существующим runtime-таблицам, оставляя старым событиям `NULL`, старым обращениям — `false`. На чистой БД runtime-таблиц во время API-миграции ещё нет: их создаёт Flue сразу с новыми полями. API и Flue в текущем Compose используют одну БД; при разделении БД миграция метаданных должна выполняться в БД Flue.

Миграция `0026` удаляет `aw_mock.samples`, `public.aw_mock_samples` с данными и индексом, затем пустую схему `aw_mock`. Рабочие таблицы не меняются, `CASCADE` не используется. Роль `aw_mock_reader` не удаляется, поскольку роли общие для кластера. При откате восстанавливается только пустая mock-структура. Если моки копировались в отдельную модель AW, эту модель нужно очистить отдельно.

Миграция `0027` удаляет исторические обращения `reset` из `support_requests` и `bars_telegram_requests`, связанные события и записи расходов. У завершённых Telegram updates очищается ссылка на удалённое обращение; сами updates, сообщения и внутренние потоки Flue не удаляются. При наличии тикета, активного update или противоречащего результата миграция прерывается целиком, не удаляя данные. `spam` не изменяется. Удаление строк необратимо без резервной копии; `downgrade` данные не восстанавливает. Причина `reset` исключена из новых API/Flue-контрактов. До миграции SQL модели уже скрывает её из аналитики.

## Обновление AW

Вручную: откройте модель, затем `Bars_Hakaton → SQL → support_requests_safe → Редактировать`, вставьте `requests.sql`, сохраните и выполните полную загрузку в хранилище. Третий виджет нужно переключить с HTML-заглушки на KPI по правилам выше.

Либо используйте идемпотентный скрипт для четырёх существующих виджетов:

```sh
node ops/aw/configure.mjs
```

Требуются Node.js 22+ и переменная окружения `AW_TOKEN` с токеном текущего сеанса AW. Получите его из собственных средств авторизации стенда, не отправляйте в чат и не сохраняйте в Git; после запуска удалите из окружения. `AW_BASE_URL` по умолчанию `https://aw-demo.ru`. HTTPS обязателен вне localhost.

Скрипт сначала проверяет доступ и принадлежность объектов модели, выполняет проверочный запрос с количеством обращений/категорий/полного учёта, обновляет SQL и четыре существующих виджета, затем запрашивает загрузку модели. Он не меняет таблицы PostgreSQL, доступы и настройки источника. Пароли и токены не выводятся.

ID стенда по умолчанию: модель `32036`, SQL-блок `114233`, источник `33540`, причины `93512`, без оператора `93513`, первый ответ `93514`, темы `93515`. Для другого стенда задайте `AW_MODEL_ID`, `AW_MODEL_OBJECT_ID`, `AW_SOURCE_ID`, `AW_REASONS_WIDGET_ID`, `AW_AUTONOMOUS_WIDGET_ID`, `AW_FIRST_ANSWER_WIDGET_ID`, `AW_TOPICS_WIDGET_ID`.

До применения миграции SQL тоже работает, но новый показатель не получает числовых данных: покрытие равно нулю. После обновления создайте новые обращения, дождитесь их закрытия/классификации и успешной загрузки AW. Исторические события не размечаются догадками по тексту.

## Ручная проверка

- Один ответ → подтверждение: один ответ, ноль уточнений, успех первого ответа.
- Уточнение → ответ → подтверждение: уточнение присутствует, успеха первого ответа нет.
- Частичный ответ и следующий вопрос: ответ и уточнение учитываются раздельно.
- Приветствие/оценка/служебная реплика не увеличивают количество ответов.
- Повторная обработка той же доставки не добавляет событие второй раз.
- Ошибка/неизвестная доставка не считается успешной отправкой.
- Старые/неполные события дают `NULL` и уменьшают покрытие, но не искажают знаменатель первого ответа.
- Для свежих закрытых обращений появляются категории; для исторических пустых категорий сохраняется явная пометка.
